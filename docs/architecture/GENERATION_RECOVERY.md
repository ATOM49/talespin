# Generation Recovery

Worldbuilder owns authorization, durable application jobs, explicit retries,
leases, and authoritative persistence. Watcher owns only infrastructure
checkpoints in the `GenerationCheckpoint` MongoDB collection. It never reads or
writes gameplay entities. Configure its database connection using the
[local development runbook](../LOCAL_DEVELOPMENT.md).

## Identity and checkpoints

The typed worldbuilder client sends `X-Generation-Id`. World and narrative jobs
use their stable MongoDB job IDs across all attempts. Standalone requests use a
hash of the endpoint and parsed input; unchanged inputs reuse their previous
results. To deliberately request fresh generation, a server caller can supply a
new generation ID. The shared header schema permits only bounded safe IDs.

Each stage has a SHA-256 checkpoint ID derived from the generation scope,
pipeline version, operation, provider/model, and complete input. Text and vision
identities also include the output JSON schema. Changed prompts, schemas,
models, or parameters produce separate records. Validated text, vision,
character profiles, gallery plans, and per-asset CDN results are saved
independently. The existing CDN fingerprint cache remains an additional reuse
layer across generation jobs.

Stage leases last 15 minutes and renew every 30 seconds. Atomic MongoDB claims
prevent two workers from performing the same active stage. Owner tokens fence
writes from superseded attempts. Successful sibling work finishes checkpointing
before a workflow reports failure; concurrency pools stop dispatching new items
once a worker fails. Checkpoints have no automatic expiry because deleting
successful results would cause future retries to spend credits again.

## Segmind recovery

Watcher selects asynchronous v2 for its Segmind image adapters. Before POST,
it records `SUBMITTING`; after acceptance, it saves the request ID before
polling. It does not automatically retry POST on network errors or 5xx replies.
The provider client resumes through status/result GET requests using that ID.
CDN uploads retry three times using the same generated bytes, without another
provider call. Each record retains its generation scope and operation for diagnosis.

| Checkpoint state                                | Retry behavior                                                         |
| ----------------------------------------------- | ---------------------------------------------------------------------- |
| `COMPLETED`                                     | Return the saved result; make no provider call.                        |
| `SUBMITTED` or expired work with a request ID   | Poll/download the existing job and retry its CDN upload.               |
| Confirmed provider `FAILED`                     | Permit a new submission for that step; retain previous IDs in history. |
| Definitively rejected submission (4xx)          | Retry the failed step after fixing the rejection.                      |
| `UNKNOWN` or expired `SUBMITTING` without an ID | Stop for reconciliation; never infer that the provider did not charge. |
| Active lease                                    | Return a conflict; preserve the running work.                          |

A world blueprint no longer silently skips failed faction/character artwork.
A matching stored CDN artifact can also recover a lost upload acknowledgement,
even when the provider submission is otherwise unresolved.
Its application job stays failed/retryable, and retry reuses completed text,
regions, gallery plans, and images. A persistence failure after the complete
blueprint still uses worldbuilder's existing blueprint checkpoint.

Synchronous OpenAI image generation/editing has no resumable provider job API
in this implementation. Completed CDN results are checkpointed, but an ambiguous
failure after submission requires reconciliation. Text failures retry the
unfinished text stage; completed validated text is never called again.

## Reconciliation

Use the watcher server environment and inspect its private checkpoint collection
for `UNKNOWN` or expired `SUBMITTING` records. Route errors also include the
checkpoint ID when available. Build watcher, then inspect one record:

```bash
cd apps/watcher
node dist/scripts/reconcile-generation.js --step <checkpoint-id>
```

If the provider dashboard shows that submission succeeded, attach its request ID
so the next normal application retry resumes it:

```bash
node dist/scripts/reconcile-generation.js --step <checkpoint-id> --request-id <provider-request-id>
```

Only after verifying that no provider job was accepted, release the checkpoint
for a fresh submission:

```bash
node dist/scripts/reconcile-generation.js --step <checkpoint-id> --confirm-not-submitted
```

If a synchronous OpenAI result was accepted but cannot be recovered from the
CDN or provider, an operator can explicitly authorize replacement with
`--confirm-result-unrecoverable`. This permits a new billable request; verify
that the result is unavailable before using it.

The tool only modifies expired unresolved submissions. It cannot overwrite
completed work or an active lease. Never remove successful sibling checkpoints
to retry one failed asset. Provider result retention is external: if an ID has
expired, a 404 is not treated as permission to spend again. Investigate the
provider record before arranging replacement.

## Verification

Provider tests use fixtures; they do not spend credits. The watcher suite covers
reused text, partial image failures, submission ambiguity, terminal failures,
concurrent claims, and wire validation. To exercise persistence and fencing
against an isolated local MongoDB instance:

```bash
RECOVERY_TEST_DATABASE_URL=mongodb://127.0.0.1:27028/test pnpm --filter @talespin/watcher test
```

The integration test creates and deletes only its own randomly named test database.
It is skipped without this variable. This does not verify paid inference,
production deployment, or provider retention guarantees.
